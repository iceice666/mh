# mh v0.2 — Workflow Runtime Specification

**Status:** Draft
**Target:** v0.2
**Previous release:** v0.1
**Primary implementation language:** Rust
**PTC runtime:** MicroQuickJS

---

## 1. Overview

`mh` v0.2 extends the existing PTC-first coding-agent harness from a **program executor** into a **workflow runtime**.

v0.1 already establishes the important execution substrate:

* disposable MicroQuickJS VM per PTC program;
* canonical synchronous `tool(name, args)` ABI;
* `read`, `write`, `edit`, `glob`, `grep`, `exec`;
* provider-side single `ptc({source})` function;
* native function-call lowering into PTC;
* bounded wall time, instruction count, tool-call count, process count, VM heap, result size and output size;
* cancellation;
* persistent append-only sessions;
* persistent result storage;
* handle-backed `exec.stdout` / `exec.stderr`;
* context priority classes;
* workspace filesystem capability checks.

These capabilities exist in the current implementation rather than merely in the previous design document.

Therefore v0.2 MUST NOT spend its scope rebuilding the v0.1 execution substrate.

The v0.2 thesis is:

> **v0.1 lets the model execute programs. v0.2 lets the model execute workflows.**

A workflow is a PTC execution that can efficiently perform multiple independent operations, expose its internal actions to the host, preserve useful working state across inference turns, accept user steering, and produce explicit verification evidence.

---

# 2. Goals

v0.2 MUST add:

1. structured per-tool runtime tracing;
2. bounded parallel `batch()` execution;
3. stronger ToolResult metadata and truncation semantics;
4. working-state-aware context compilation;
5. real context-budget enforcement;
6. mid-task steering at safe execution boundaries;
7. structured PTC diagnostics;
8. repeated-action detection;
9. explicit verification evidence;
10. filesystem capability correctness and safer subprocess environment handling.

v0.2 SHOULD preserve the architectural property that:

> JavaScript remains synchronous and simple; concurrency belongs to the Rust host.

---

# 3. Non-Goals

v0.2 does **not** include:

* Promise / async JavaScript;
* generic `spawn()` / `join()` futures;
* subagents;
* multi-agent scheduling;
* plugin APIs;
* MCP;
* browser automation;
* generic provider marketplace;
* model routing;
* generic rollback transactions;
* full container sandboxing;
* network tooling;
* daemon mode;
* remote execution;
* GUI/TUI framework;
* semantic RAG;
* vector storage.

In particular, **generic checkpoint/rollback is deferred**.

The current `exec` primitive can execute arbitrary workspace processes, and those processes may mutate files outside the visibility of `write()` and `edit()`. A rollback system implemented only around mh filesystem tools would therefore provide misleading transactional semantics.

Rollback SHOULD only be introduced once process-side mutations can be captured through an overlay, worktree, filesystem snapshot, or equivalent mechanism.

---

# 4. Current Baseline

The current agent loop is:

```text
compile context
      ↓
model
      ↓
Text ───────────────▶ finish

Program / FC
      ↓
lower to PTC
      ↓
MicroQuickJS
      ↓
PTC result
      ↓
next inference
```

This architecture SHOULD remain.

The current implementation already lowers executable model output through a single PTC path rather than maintaining separate native-tool and PTC executors.

v0.2 extends this path rather than replacing it:

```text
                    ┌─────────────────┐
                    │      Model      │
                    └────────┬────────┘
                             │
                        canonical PTC
                             │
                             ▼
┌─────────────────────────────────────────────┐
│              MicroQuickJS VM                │
│                                             │
│ tool()     batch()      evidence()          │
└──────┬─────────┬──────────────┬─────────────┘
       │         │              │
       ▼         ▼              ▼
  Tool Host   Scheduler      Trace Sink
       │         │              │
       └─────────┴──────┬───────┘
                        ▼
                 Session / WorkState
                        │
                        ▼
                Context Compiler v2
```

---

# 5. Core Invariants

v0.2 adds the following invariants.

## I. Every host operation is observable

Every PTC host call MUST produce structured runtime events.

A PTC program must no longer be opaque from:

```text
PtcStarted
    ...
PtcCompleted
```

The host must know what occurred in between.

---

## II. Parallelism never requires asynchronous JavaScript

PTC remains synchronous from the model's perspective.

```js
var results = batch("read", requests);
```

blocks until its host work completes.

No Promise or event-loop semantics are introduced.

---

## III. Context budget is a real upper bound

`ContextCompiler::max_tokens` MUST no longer be advisory.

The compiler MUST NOT silently produce a context larger than the configured maximum because too many items were classified `Hard`.

---

## IV. Queued steering invalidates stale unexecuted actions

If the user sends new steering while a model request is running, and that model request returns a PTC program which has not yet started, mh MUST NOT blindly execute that stale program.

The steering is applied first.

---

## V. Large-result truncation is visible

The model-generated PTC program MUST be able to determine whether a ToolResult contains the complete output or only a retained portion.

---

# 6. Structured PTC Trace

v0.1 records PTC executions at session level, but individual PTC tool calls are not persisted; the session sees `PtcStarted` and `PtcCompleted/PtcFailed`, while `AgentEvent::ToolCompleted` reports only aggregate tool count and duration.

v0.2 MUST introduce a structured runtime event stream.

Recommended representation:

```rust
pub enum PtcEvent {
    HostCallStarted {
        call_id: u64,
        name: String,
        args_hash: u64,
        batch: Option<BatchItem>,
    },

    HostCallCompleted {
        call_id: u64,
        name: String,
        outcome: HostCallOutcome,
        effect: ToolEffect,
        duration_ms: u64,
        result_ids: Vec<ResultId>,
    },

    EvidenceRecorded {
        evidence: EvidenceRecord,
    },
}
```

`args_hash` allows loop detection without persisting arbitrarily large model-generated arguments.

A bounded argument preview MAY additionally be stored for debugging.

---

# 7. Tool Effects

Every host tool MUST declare a coarse effect class.

```rust
pub enum ToolEffect {
    ReadOnly,
    WorkspaceMutation,
    Process,
    Meta,
}
```

Initial mapping:

```text
read      → ReadOnly
glob      → ReadOnly
grep      → ReadOnly

write     → WorkspaceMutation
edit      → WorkspaceMutation

exec      → Process

evidence  → Meta
batch     → derived from child operations
```

This is not intended to become a generic effect-system framework.

The classification exists specifically for:

* working-state generation;
* verification;
* loop detection;
* tracing;
* future policy decisions.

---

# 8. Session Trace Events

The durable event log MUST retain meaningful runtime actions.

Recommended additions:

```rust
SessionEvent::ToolCompleted {
    call_id: u64,
    name: String,
    args_hash: u64,
    effect: ToolEffect,
    ok: bool,
    duration_ms: u64,
    result_ids: Vec<ResultId>,
}

SessionEvent::EvidenceRecorded {
    evidence: EvidenceRecord,
}

SessionEvent::SteeringQueued {
    content: String,
}

SessionEvent::RepeatedActionDetected {
    fingerprint: String,
}
```

Large tool arguments and outputs MUST NOT be copied into `session.jsonl`.

Result data continues to belong in the Result Store.

---

# 9. `batch()`

`batch()` is the primary new PTC execution primitive in v0.2.

Canonical form:

```js
var results = batch("read", [
    { path: "src/a.rs" },
    { path: "src/b.rs" },
    { path: "src/c.rs" }
]);
```

The operation returns only after every scheduled item has reached a terminal state.

---

## 9.1 Semantics

`batch()` MUST:

* preserve input ordering;
* use bounded host-side concurrency;
* count every child operation against the normal tool-call budget;
* count every child `exec` against the process budget;
* support cancellation;
* isolate child tool errors;
* produce the same logical result for each item as a direct call to that tool.

Example:

```js
var r = batch("read", [
    { path: "a.rs" },
    { path: "missing.rs" },
    { path: "c.rs" }
]);

return r;
```

may produce:

```json
[
  {
    "path": "a.rs",
    "content": "...",
    "totalLines": 40,
    "truncated": false
  },
  {
    "error": "read missing.rs: ..."
  },
  {
    "path": "c.rs",
    "content": "...",
    "totalLines": 10,
    "truncated": false
  }
]
```

One failed item MUST NOT fail the entire batch.

---

## 9.2 Batch-safe tools

v0.2 MUST support:

```text
read
grep
glob
exec
```

through `batch()`.

`write` and `edit` SHOULD initially be rejected:

```json
{
  "error": "tool 'edit' is not batch-safe"
}
```

Parallel mutation introduces overlapping-write ordering and transactional questions that are not necessary for v0.2.

---

## 9.3 Concurrency budget

`PtcBudget` gains:

```rust
pub max_parallel_tools: usize,
```

Recommended default:

```text
8
```

Actual concurrency is:

```text
min(
    batch length,
    max_parallel_tools,
    remaining relevant resource budget
)
```

For `exec`, `max_processes` remains authoritative.

---

## 9.4 No nested uncontrolled fan-out

Nested batches MAY be rejected in v0.2.

The runtime SHOULD prefer predictable bounded execution over recursive fan-out.

---

# 10. ToolResult v2

v0.1 already implements host-backed handles with:

```text
.read()
.head()
.tail()
.grep()
.json()
.length
```

rather than materializing complete subprocess output into MicroQuickJS.

v0.2 therefore extends rather than replaces this API.

---

## 10.1 Required metadata

Every blob handle SHOULD expose:

```js
result.id
result.length
result.totalBytes
result.truncated
result.kind
```

Semantics:

```text
length       bytes actually retained by ResultStore
totalBytes   bytes produced before retention/truncation
truncated    totalBytes > length
kind         e.g. "stdout", "stderr"
```

`length` remains for v0.1 compatibility.

---

## 10.2 Persist original length

The current result store retains only capped data and marks whether truncation occurred.

v0.2 SHOULD extend persisted result metadata:

```rust
struct StoredResult {
    id: ResultId,
    data: Vec<u8>,
    total_bytes: u64,
    truncated: bool,
}
```

The store remains bounded.

v0.2 does **not** require retaining unlimited command output.

---

## 10.3 Exec metadata

`exec()` SHOULD return:

```js
{
    exitCode,
    durationMs,

    stdout: ResultHandle,
    stderr: ResultHandle
}
```

Truncation information belongs directly on each handle.

The current internal `stdoutTruncated` / `stderrTruncated` values are generated by `exec` but are not included in the JS-visible object produced by `exec_result_to_vm`; v0.2 MUST close this information gap.

---

# 11. Collection Truncation Metadata

`grep` and `glob` currently expose ergonomic array results to PTC, but truncation metadata can be lost when the host wrapper extracts only the array.

v0.2 MUST make truncation observable.

Preferred API:

```js
var matches = grep(...);

matches.truncated
matches.length
```

and:

```js
var files = glob(...);

files.truncated
files.length
```

The collection remains directly iterable:

```js
for (var i = 0; i < matches.length; i++) {
    ...
}
```

This keeps the v0.1 ergonomic API while exposing correctness metadata.

---

# 12. Working State

v0.2 introduces a derived `WorkState`.

`WorkState` is not a second source of truth.

It is reconstructed from the append-only event stream.

Recommended structure:

```rust
pub struct WorkState {
    pub objective: Option<String>,

    pub latest_user_message: Option<String>,

    pub touched_files: Vec<String>,

    pub latest_ptc: Option<PtcSummary>,
    pub latest_failure: Option<PtcSummary>,

    pub mutation_epoch: u64,

    pub evidence: Vec<EvidenceRecord>,
}
```

---

# 13. Mutation Epoch

Every successful:

```text
write
edit
```

increments the logical `mutation_epoch`.

Example:

```text
epoch 0
  read
  grep

edit foo.rs

epoch 1
  cargo test
  evidence(tests, pass)

edit bar.rs

epoch 2
```

Evidence from epoch 1 does not verify epoch 2.

`exec` is classified separately as `Process`; v0.2 does not claim to know whether an arbitrary subprocess changed source files.

---

# 14. Context Compiler v2

The current compiler has priority-aware selection, but every historical `UserMessage` is currently classified `Hard`, so hard content may grow independently of the configured token budget. `Compacted` exists as an event type but there is no runtime compaction workflow using it.

v0.2 MUST fix this.

---

## 14.1 Context layout

Recommended output:

```text
[system]

[objective]

[current user instruction]

[working state]
- touched files
- latest failure
- latest evidence
- mutation epoch

[recent conversation]

[latest relevant PTC result]

[older compacted state, if any]
```

---

## 14.2 Priority policy

Only these items SHOULD normally be `Hard`:

```text
system prompt
root objective
latest unapplied user steering/current instruction
```

Older user messages MUST NOT all remain permanently `Hard`.

Recommended mapping:

```text
System                         Hard
Objective                      Hard
Current user instruction       Hard

WorkState                      Sticky
Latest relevant assistant      Sticky

Latest PTC result              Working
Latest PTC failure             Working

Old dialogue                   Ephemeral
Old PTC results                Ephemeral
```

---

## 14.3 Hard-overflow behavior

The following invariant MUST hold:

```text
compiled.estimated_tokens <= max_tokens
```

If required hard information alone exceeds the context budget, the compiler MUST return an explicit overflow condition instead of silently exceeding the configured maximum.

Example:

```rust
ContextError::HardOverflow {
    required_tokens,
    max_tokens,
}
```

The agent may then produce a diagnostic or bounded representation.

---

# 15. Deterministic Compaction

v0.2 SHOULD first compact **state**, not prose.

Before considering an additional model inference for summarization, mh should derive compact state from events:

```text
50 old PTC executions
        ↓
latest successful result
latest failure
touched files
current evidence
```

Old raw PTC result messages SHOULD disappear from the active context while remaining durable in `session.jsonl`.

Likewise:

```text
old tool traces
    ↓
WorkState
```

This gives mh a useful form of compaction without periodically asking the model to summarize its own conversation.

Semantic model-generated compaction MAY remain deferred.

---

# 16. Steering

The current interactive CLI executes `send_message_with_events()` synchronously; while the agent is running, stdin is not concurrently processed as steering.

v0.2 MUST support queued mid-task steering.

Example:

```text
mh> refactor this parser

[agent running...]

mh> don't change the public API
```

The second message is queued as steering rather than waiting until the entire first task terminates.

---

# 17. Steering Safe Points

Steering is applied only at explicit safe points.

Required safe points:

```text
after model response
before PTC execution
after PTC execution
before next model request
```

---

## 17.1 Steering during model inference

If steering arrives while the model is generating:

```text
model starts
   │
   ├──── user steering arrives
   │
model returns PTC
```

mh MUST detect pending steering **before executing the PTC**.

The generated PTC is stale.

Required behavior:

```text
discard unexecuted PTC
append steering
recompile context
request model again
```

This avoids executing modifications that were generated before a new constraint arrived.

---

## 17.2 Steering during PTC

If steering arrives after PTC execution has already begun:

```text
PTC running
   │
user steering arrives
```

normal steering SHOULD be queued until the execution completes.

Explicit cancellation remains available through Ctrl-C.

v0.2 does not attempt to mutate live JavaScript lexical state.

---

# 18. Agent Control Channel

Recommended host abstraction:

```rust
pub enum AgentControl {
    Steer(String),
    Interrupt,
}
```

The agent receives controls through a channel independent from streamed `AgentEvent`s.

Conceptually:

```text
             ┌──────── CLI input ────────┐
             │                           ▼
Agent ───────┼──────────────────── Control Queue
  │          │
  └──── AgentEvent ───────────────▶ Renderer
```

The exact CLI threading model is implementation-defined.

---

# 19. Evidence

v0.2 introduces an explicit PTC meta primitive:

```js
evidence(kind, ok, metadata)
```

Example:

```js
var test = exec({
    command: ["cargo", "test"]
});

evidence("tests", test.exitCode === 0, {
    command: "cargo test",
    stdout: test.stdout.id,
    stderr: test.stderr.id
});

return {
    passed: test.exitCode === 0
};
```

---

## 19.1 Evidence record

```rust
pub struct EvidenceRecord {
    pub kind: String,
    pub ok: bool,

    pub mutation_epoch: u64,

    pub result_ids: Vec<ResultId>,
    pub note: Option<String>,

    pub timestamp_ms: u64,
}
```

Evidence belongs to the host/session state, not only the PTC return value.

---

## 19.2 Evidence is not another tool

`evidence()`:

* does not access the OS;
* SHOULD NOT count against process budget;
* MAY count against a separate metadata-call limit;
* emits `PtcEvent::EvidenceRecorded`.

---

# 20. Completion Awareness

v0.2 SHOULD make verification state visible to the model:

```text
Working state:
- workspace modified: yes
- mutation epoch: 4
- latest successful evidence: epoch 3
- current changes verified: no
```

This is enough for the model to decide to run verification.

A strict hard completion gate MAY be deferred.

v0.2 SHOULD prefer awareness over introducing a complicated policy engine.

---

# 21. Structured PTC Diagnostics

v0.1 surfaces MicroQuickJS exceptions back to the model and already has an integration test ensuring unsupported syntax such as `let` becomes a repairable failure.

v0.2 MUST standardize this into structured diagnostics.

Recommended form:

```rust
pub struct PtcDiagnostic {
    pub kind: PtcDiagnosticKind,
    pub message: String,
    pub line: Option<u32>,
    pub column: Option<u32>,
    pub hint: Option<String>,
}
```

Kinds:

```rust
Syntax
Runtime
UnsupportedSyntax
ToolBudget
ProcessBudget
InstructionBudget
WallTime
Cancelled
```

Example model-visible failure:

```json
{
  "ptcError": {
    "kind": "unsupported_syntax",
    "line": 1,
    "column": 1,
    "message": "unsupported lexical declaration",
    "hint": "MicroQuickJS PTC uses var; replace let/const with var"
  }
}
```

---

# 22. Compatibility Policy

v0.2 MUST retain the existing philosophy:

> runtime aliases first, source rewriting last.

Current aliases already include:

```text
tool(...)
call_tool(...)

read(...)
write(...)
edit(...)
glob(...)
grep(...)
exec(...)

tools.read(...)
tools.exec(...)
...
```

v0.2 adds `batch()` and `evidence()` to the canonical prompt.

It does **not** add a general JavaScript transpiler.

Unsupported syntax SHOULD normally produce a structured diagnostic and let the model repair its program.

---

# 23. Repeated-Action Detection

v0.2 SHOULD detect obvious non-progress loops.

Initial implementation can operate at agent-turn granularity.

Fingerprint:

```text
hash(
    normalized PTC source,
    PTC outcome,
    compact returned value
)
```

If the same effective operation produces the same result repeatedly without intervening user input, mh emits:

```text
RepeatedActionDetected
```

and injects:

```text
The previous action was repeated without changing the result.
Choose a different approach instead of retrying the same PTC program.
```

A simple initial policy:

```text
same fingerprint twice → warning
same fingerprint three times → do not execute third identical program
```

Per-tool trace enables more advanced detection later.

---

# 24. Filesystem Capability Correctness

v0.1 separates filesystem access through `Capabilities`, but the existing `resolve()` path is lexical while `write()` and `edit()` use that path directly; existing symlink targets therefore require additional handling if the workspace boundary is to be a reliable filesystem invariant.

v0.2 MUST add a write-safe resolution path.

Recommended interface:

```rust
resolve_existing_read(...)
resolve_for_write(...)
```

`resolve_for_write()` MUST:

1. reject lexical `..`;
2. canonicalize the nearest existing ancestor;
3. verify that ancestor is inside canonical workspace root;
4. if the target already exists, canonicalize the target and verify it too;
5. reject symlink-based workspace escape.

---

# 25. Process Capability Semantics

`exec` currently uses arbitrary `Command::new(...)` with workspace as `cwd`; it is not an OS filesystem/network sandbox.

v0.2 MUST make this distinction explicit.

The capability model SHOULD represent:

```rust
pub enum ProcessPolicy {
    Disabled,
    WorkspaceCwd,
}
```

rather than implying that a false `network` field necessarily prevents subprocess networking.

`WorkspaceCwd` means:

> The subprocess starts in the workspace and is controlled for lifetime/output, but otherwise runs with host OS capabilities unless a future sandbox backend says otherwise.

Full subprocess sandboxing remains deferred.

---

# 26. Subprocess Secret Scrubbing

Provider credentials MUST NOT be unnecessarily inherited by model-generated subprocesses.

Before spawning `exec`, mh MUST remove at minimum:

```text
MH_API_KEY
OPENAI_API_KEY
```

from the child environment.

Additional provider credentials SHOULD be removed as adapters are added.

The rest of the development environment may continue to be inherited in v0.2 to avoid breaking normal build tools.

A future sandbox/environment policy may become stricter.

---

`AgentEvent` SHOULD expose enough information for CLI rendering without reading session storage.

Recommended additions:

AgentEvent::PtcHostCallStarted {

AgentEvent::PtcHostCallCompleted {
    call_id,
    name,

AgentEvent::SteeringQueued

The default CLI MAY keep these terse.

Example:

```text

```

# 30. Example v0.2 Workflow

User:

```text
find the unsafe unwraps in src/, fix the obvious ones, and verify it
```

Possible PTC:

```js
var files = glob("src/**/*.rs");

var queries = [];
for (var i = 0; i < files.length; i++) {
    queries.push({
        pattern: ".unwrap()",
        path: files[i]
    });
}

var scans = batch("grep", queries);

var targets = [];
for (var i = 0; i < scans.length; i++) {
    if (scans[i].length > 0) {
        targets.push({
            path: files[i],
            matches: scans[i]
        });
    }
}

return targets;
```

After reasoning, a later PTC may edit several selected locations and verify:

```js
edit({
    path: "src/foo.rs",
    old: "value.unwrap()",
    new: "value?"
});

var tests = exec({
    command: ["cargo", "test"]
});

evidence("tests", tests.exitCode === 0, {
    stdout: tests.stdout.id,
    stderr: tests.stderr.id
});

return {
    ok: tests.exitCode === 0,
    errors: tests.exitCode === 0
        ? null
        : tests.stderr.tail(100)
};
```

The next inference sees:

```text
Working state:
- touched files: src/foo.rs
- mutation epoch: 1
- tests: PASS at epoch 1
```

rather than needing all previous raw tool calls in context.

---

# 31. Example Steering

```text
User:
refactor the parser

Model inference begins

User:
don't change the Parser public methods

Model returns a PTC program that changes Parser methods
```

Required mh behavior:

```text
model program generated
        ↓
safe-point check
        ↓
pending steering found
        ↓
discard unexecuted program
        ↓
append steering
        ↓
recompile context
        ↓
new inference
```

The stale mutation MUST NOT run.

# 32. Implementation Order

## Phase A — Runtime observability

* add `PtcEvent`;
* add event sink to `PtcRuntime`;
* emit per-host-call events;
* persist compact `ToolCompleted` events;
* derive initial `WorkState`.

This is foundational for later features.

---

## Phase B — Result ABI correctness

* persist `total_bytes`;
* expose `truncated`;
* expose `totalBytes`;
* expose exec duration;
* preserve grep/glob truncation metadata.

---

## Phase C — Batch

* add `batch()` global;
* add `max_parallel_tools`;
* parallel read/grep/glob;
* parallel exec;
* cancellation;
* stable ordering;
* tracing for batch children.

---

## Phase D — Context v2

* introduce WorkState context section;
* stop making every historical UserMessage Hard;
* enforce max token budget;
* aggressively retire old PTC results from active context;
* deterministic event projection.

---

## Phase E — Steering

* add control channel;
* concurrent interactive input;
* pending-steering queue;
* stale-program suppression;
* steering events.

---

## Phase F — Verification and resilience

* add `evidence()`;
* mutation epochs;
* structured PTC diagnostics;
* repeated-action detection.

---

## Phase G — Capability fixes

* symlink-safe writes;
* subprocess secret scrubbing;
* clarify process capability semantics.

Capability correctness MAY be implemented earlier if convenient.

---

# 35. Success Criteria

v0.2 is successful when the following task class is substantially better than v0.1:

> inspect many files → run several independent operations → make changes → verify → respond to user steering

Specifically:

### Parallelism

Reading/searching N independent targets does not require N serial host waits when the operations are batch-safe.

### Observability

Given a session event log, mh can determine which host tools ran and which workspace paths were explicitly mutated.

### Context stability

Long-running sessions do not retain every historical user message and every PTC result as mandatory context.

### Steering safety

New user constraints received before a generated PTC begins prevent that stale PTC from executing.

### Verification awareness

mh can distinguish:

```text
workspace changed + verified
```

from:

```text
workspace changed + not yet verified
```

### PTC remains small

None of these capabilities require:

```text
Promise
async/await
Node.js
plugin framework
agent framework
```
