# mh v0.4 — Delegation Runtime Specification

**Status:** Provisional
**Target:** v0.4
**Depends on:** mh v0.3 Workspace State Runtime
**Primary implementation language:** Rust
**PTC runtime:** MicroQuickJS

---

## 1. Overview

`mh` v0.4 introduces delegated reasoning and isolated execution.

It does **not** introduce a generic multi-agent framework.

The core abstraction is:

> **delegation is an execution primitive, not a persona primitive.**

A parent agent may delegate a bounded task to a child execution with an explicit workspace access mode.

Example:

```js
var report = delegate({
    task: "Inspect the parser architecture and identify the likely source of the failing precedence tests.",
    access: "read"
});
```

or:

```js
var implementation = delegate({
    task: "Implement the parser fix and verify the parser tests.",
    access: "isolated-write"
});
```

A child gets:

* its own model context;
* its own inference loop;
* bounded resources;
* explicit workspace revision;
* explicit access policy;
* structured result.

A child does not automatically inherit the full parent conversation.

The release thesis is:

> **v0.3 makes workspace state explicit.
> v0.4 makes reasoning branches explicit.**

---

# 2. Dependency on v0.3

v0.4 assumes v0.3 provides:

```text
TaskId
ExecutionId
RevisionId
WorkspaceRevision
WorkspaceDelta
revision-based evidence
checkpoint / restore
live durable events
task episodes
```

If those semantics change during v0.3 implementation, this spec MUST be audited before v0.4 implementation begins.

---

# 3. Goals

v0.4 SHOULD provide:

1. `delegate()`;
2. child task identity;
3. child execution identity;
4. read-only delegation;
5. isolated writable delegation;
6. bounded parallel delegation;
7. child-specific context compilation;
8. structured child results;
9. revision-aware child provenance;
10. parent/child cancellation;
11. delegated evidence;
12. explicit integration of child workspace changes;
13. conflict detection;
14. child lifecycle persistence.

---

# 4. Non-Goals

v0.4 does not include:

* personas;
* agent teams;
* agent chat rooms;
* arbitrary peer-to-peer messaging;
* autonomous swarm topology;
* global agent registry;
* role marketplace;
* persistent background agents;
* agent voting frameworks;
* debate mode;
* distributed hosts;
* remote execution;
* dynamic plugin agents;
* mandatory model routing.

There is one structural relationship:

```text
parent
  ↓
child delegation
```

Nested delegation MAY be disabled initially.

---

# 5. Delegation Primitive

Canonical PTC API:

```js
delegate({
    task: "...",
    access: "read"
});
```

or:

```js
delegate({
    task: "...",
    access: "isolated-write"
});
```

---

# 6. Access Modes

Initial stable modes:

```text
read
isolated-write
```

Optional future modes:

```text
shared-write
```

`shared-write` SHOULD NOT be implemented in initial v0.4.

---

# 7. Read Delegation

`access: "read"` means:

```text
child sees revision R
child cannot mutate workspace
child cannot run mutating process operations
```

It receives a read-only capability set.

Allowed:

```text
read
glob
grep
read-only exec if process policy allows it
```

However arbitrary `exec` cannot generally be proven read-only.

Therefore the initial implementation MAY simply disable `exec` for read children.

That is preferred over pretending a subprocess is read-only.

---

# 8. Isolated-Write Delegation

`access: "isolated-write"` means:

```text
parent workspace @ R10
        │
        └── isolated child workspace based on R10
                   │
                   ├── child edits
                   ├── child exec
                   └── child verification
                           ↓
                         R15'
```

The parent workspace remains unchanged while the child runs.

---

# 9. Isolation Backend

For Git workspaces, preferred implementation:

```text
Git worktree
```

or equivalent hidden workspace materialization.

Example:

```text
.mh/workspaces/<execution-id>/
```

The child works against its own filesystem.

The parent remains on its original revision.

---

# 10. No Shared Writable CWD

Initial v0.4 MUST NOT run multiple writable agents against the same live workspace.

This architecture is explicitly rejected:

```text
parent ──┐
child A ─┼── same cwd
child B ─┘
```

---

# 11. Delegated Task

A child is represented as:

```rust
pub struct DelegatedTask {
    pub task_id: TaskId,
    pub parent_task_id: TaskId,

    pub execution_id: ExecutionId,
    pub parent_execution_id: ExecutionId,

    pub objective: String,

    pub access: DelegationAccess,

    pub base_revision: RevisionId,
}
```

---

# 12. DelegationAccess

```rust
pub enum DelegationAccess {
    Read,
    IsolatedWrite,
}
```

No generic capability object is exposed to the model.

---

# 13. Child Context

The child MUST NOT automatically receive:

```text
entire parent conversation
```

Recommended child context:

```text
[system]
child execution policy

[delegated objective]
...

[parent-provided context]
...

[workspace state]
revision R10
```

The child can inspect the workspace itself through PTC.

---

# 14. Parent Context Selection

The parent MAY provide:

```js
delegate({
    task: "...",
    access: "read",
    context: {
        note: "The failing tests are parser::precedence_*"
    }
});
```

This is bounded structured context.

The harness does not forward arbitrary hidden model reasoning.

---

# 15. Child Agent Loop

A child runs the same fundamental loop as the parent:

```text
context
↓
model
↓
PTC
↓
context
↓
model
↓
final result
```

It SHOULD reuse:

```text
Model
ContextCompiler
PtcRuntime
ResultStore abstraction
WorkspaceTracker
```

No second agent runtime should be invented.

---

# 16. Delegation Result

`delegate()` returns a structured object.

Recommended:

```js
{
    ok: true,

    summary: "...",

    baseRevision: "R10",
    finalRevision: "R10",

    changed: false,

    evidence: [...]
}
```

For isolated-write child:

```js
{
    ok: true,

    summary: "...",

    baseRevision: "R10",
    finalRevision: "R15-child",

    changed: true,

    workspace: {
        id: 7
    },

    evidence: [...]
}
```

---

# 17. Do Not Return Child Transcript

The parent MUST NOT receive the child's full dialogue.

The child returns:

```text
summary
structured findings
revision information
evidence references
optional isolated workspace handle
```

This prevents delegation from becoming context dumping.

---

# 18. Child Output Contract

A child SHOULD finish with a structured `DelegateResult`.

Recommended host representation:

```rust
pub struct DelegateResult {
    pub task_id: TaskId,
    pub execution_id: ExecutionId,

    pub ok: bool,

    pub summary: String,

    pub base_revision: RevisionId,
    pub final_revision: RevisionId,

    pub workspace: Option<IsolatedWorkspaceId>,

    pub evidence: Vec<EvidenceRecord>,
}
```

---

# 19. Structured Findings

A child MAY also return:

```rust
pub findings: Value
```

but the total serialized size MUST be bounded.

Large raw child output belongs in ResultStore.

---

# 20. Parallel Delegation

v0.4 SHOULD support:

```js
delegate_batch([
    {
        task: "Inspect parser implementation",
        access: "read"
    },
    {
        task: "Inspect parser tests",
        access: "read"
    }
]);
```

or equivalent:

```js
batch("delegate", ...)
```

Whether `delegate` integrates with generic `batch()` or has a dedicated primitive is implementation-defined.

---

# 21. Model Parallelism Budget

Introduce:

```rust
pub struct DelegationBudget {
    pub max_children: usize,
    pub max_parallel_children: usize,
    pub max_child_turns: usize,
}
```

Recommended conservative defaults:

```text
max children per parent task: 8
max parallel children: 4
```

---

# 22. Resource Accounting

Child execution MUST count separately for:

```text
model turns
PTC tool calls
process calls
wall time
```

The parent has an aggregate delegation budget.

This prevents:

```text
one delegate call
→ unbounded recursive computation
```

---

# 23. No Recursive Delegation Initially

Initial v0.4 SHOULD disallow:

```text
child delegates child
```

Maximum delegation depth:

```text
1
```

The data model MAY include depth for future use.

---

# 24. Parent Cancellation

If parent task is interrupted:

```text
all active children
```

MUST receive cancellation.

---

# 25. Child Cancellation

Parent PTC MAY support:

```js
cancel_delegate(id)
```

only if needed.

Initial version may simply cancel all active children when the parent execution is cancelled.

---

# 26. Steering

User steering applies to the parent task.

It does not automatically rewrite already-running child objectives.

If steering materially invalidates a child:

```text
parent may cancel child
```

or ignore its eventual result.

Initial policy:

```text
steering supersedes parent inference
active children remain running unless parent is cancelled
```

This may be revisited based on real usage.

---

# 27. Read Child Freshness

A read child starts at:

```text
base revision R10
```

If parent workspace later moves to:

```text
R12
```

the child's result is still valid as:

```text
analysis of R10
```

but not necessarily applicable to R12.

The parent receives the base revision explicitly.

---

# 28. Isolated Child Freshness

An isolated child always reports:

```text
base revision
final isolated revision
```

The parent can determine whether its own workspace diverged meanwhile.

---

# 29. Integration

Writable child work is **not automatically merged** into the parent.

The parent must explicitly integrate it.

Potential PTC API:

```js
integrate(child.workspace);
```

---

# 30. Integration Preconditions

Suppose:

```text
child base = R10
child final = C15

parent current = R10
```

Integration is straightforward.

If:

```text
parent current = R13
```

the parent diverged.

mh MUST detect this.

---

# 31. Conflict Result

Integration MUST return structured conflict information.

Example:

```js
{
    ok: false,
    conflict: true,

    childBase: "R10",
    parentCurrent: "R13",

    paths: [
        "src/parser.rs"
    ]
}
```

No silent overwrite.

---

# 32. Integration Backend

For Git workspaces, integration MAY use:

```text
diff/patch application
three-way merge
temporary commit/cherry-pick
```

Implementation is not stable API.

The visible semantics are:

```text
apply child delta
or
return conflict
```

---

# 33. Integration Creates Parent Revision

Successful integration:

```text
parent R13
   +
child delta
   ↓
parent R14
```

MUST emit normal v0.3:

```text
WorkspaceRevisionChanged
```

events.

---

# 34. Child Evidence

Child evidence remains attributed to:

```text
child revision
child TaskId
child ExecutionId
```

It is never rewritten to pretend it verified the parent revision.

---

# 35. Evidence After Integration

If integration reproduces the exact verified child state in the parent, mh MAY later support evidence transfer.

Initial v0.4 SHOULD be conservative:

```text
child evidence remains child evidence
parent should re-verify after integration
```

This keeps semantics obvious.

---

# 36. Delegated Verification

A useful pattern:

```text
parent implements
↓
read-only reviewer child
↓
review result
```

Read child can inspect:

```text
parent revision R20
```

and return:

```text
review of R20
```

This is naturally revision-correct.

---

# 37. Reviewer Is Not a Role Primitive

The model may delegate:

```js
delegate({
    task: "Review the current implementation for correctness and identify likely regressions.",
    access: "read"
});
```

There is no built-in:

```text
ReviewerAgent
ResearcherAgent
CoderAgent
```

The task defines behavior.

---

# 38. Model Selection

Initial v0.4 MAY use the same model for parent and child.

Optional child model field:

```js
delegate({
    task: "...",
    access: "read",
    model: "fast"
});
```

SHOULD be deferred unless model routing already exists.

Delegation does not require routing.

---

# 39. Session Events

Recommended:

```rust
SessionEvent::DelegationStarted {
    parent_task_id: TaskId,
    parent_execution_id: ExecutionId,

    child_task_id: TaskId,
    child_execution_id: ExecutionId,

    access: DelegationAccess,
    base_revision: RevisionId,
}

SessionEvent::DelegationCompleted {
    child_task_id: TaskId,
    child_execution_id: ExecutionId,

    ok: bool,
    final_revision: RevisionId,
}

SessionEvent::DelegationCancelled {
    child_task_id: TaskId,
    child_execution_id: ExecutionId,
}
```

---

# 40. Integration Events

Recommended:

```rust
SessionEvent::IntegrationStarted {
    child_execution_id: ExecutionId,
    child_base: RevisionId,
    parent_base: RevisionId,
}

SessionEvent::IntegrationCompleted {
    child_execution_id: ExecutionId,
    parent_revision: RevisionId,
}

SessionEvent::IntegrationConflict {
    child_execution_id: ExecutionId,
    paths: Vec<String>,
}
```

---

# 41. Child Storage

Child session data MAY live under:

```text
.mh/tasks/<task-id>/
```

or remain in one append-only parent event log with task IDs.

Preferred architecture:

```text
single durable event store
+
TaskId / ExecutionId provenance
```

Avoid proliferating unrelated session databases.

---

# 42. Child ResultStore

Large child outputs MAY use the same underlying persistent blob store.

`ResultId` SHOULD remain globally unique within the workspace session.

This allows the parent to inspect referenced child evidence without copying blobs.

---

# 43. Child Working State

Child context uses the same WorkState semantics as v0.3:

```text
task objective
base revision
current child revision
changed paths
verification evidence
```

No child-specific context framework is needed.

---

# 44. PTC Surface v0.4

Proposed additions:

```js
delegate(options)
integrate(workspace)
```

Optional:

```js
delegate_batch(options[])
```

Existing primitives remain unchanged.

---

# 45. Example: Read Delegation

```js
var investigations = delegate_batch([
    {
        task: "Inspect the parser implementation and explain how precedence is represented.",
        access: "read"
    },
    {
        task: "Inspect parser tests and identify the exact failing behavior.",
        access: "read"
    }
]);

return investigations;
```

Parent receives two compact reports, not two conversation transcripts.

---

# 46. Example: Isolated Implementation

```js
var child = delegate({
    task: "Implement the parser precedence fix and run the parser tests.",
    access: "isolated-write"
});

if (!child.ok) {
    return child;
}

return {
    summary: child.summary,
    workspace: child.workspace,
    evidence: child.evidence
};
```

Later parent:

```js
var merged = integrate(child.workspace);

if (!merged.ok) {
    return merged;
}

var tests = exec({
    command: ["cargo", "test", "parser"]
});

evidence("parser tests", tests.exitCode === 0, {
    stdout: tests.stdout.id,
    stderr: tests.stderr.id
});

return {
    integrated: true,
    tests: tests.exitCode
};
```

---

# 47. Example: Divergence Conflict

```text
child based on R20

child changes:
src/parser.rs

meanwhile parent:
R20 → R22

parent also changes:
src/parser.rs
```

Integration:

```text
conflict
```

not:

```text
last writer wins
```

---

# 48. Delegation vs PTC Batch

Use PTC `batch()` when work is procedural:

```text
read many files
grep patterns
run commands
```

Use `delegate()` when work requires independent model reasoning:

```text
analyze architecture
review a design
develop an alternative implementation
investigate an unfamiliar subsystem
```

This distinction SHOULD appear in the system prompt.

---

# 49. Delegation Heuristic

The harness itself SHOULD NOT contain a task classifier deciding when to delegate.

The model chooses:

```text
batch
vs
delegate
```

based on prompt guidance.

This preserves mh's opinionated but simple architecture.

---

# 50. Failure Semantics

Child failure returns a normal structured result.

For example:

```js
{
    ok: false,
    summary: "Could not reproduce the failure.",
    ...
}
```

A child failure MUST NOT automatically fail the parent PTC execution.

---

# 51. Child Crash Recovery

An isolated child SHOULD be resumable from its durable task/execution state where practical.

Initial v0.4 MAY instead mark the child failed after process restart, provided:

* its isolated workspace survives;
* its final known revision is retained;
* the parent can inspect or discard it.

---

# 52. Garbage Collection

Completed isolated workspaces MAY be retained until:

```text
integrated
discarded
parent task completed
```

A cleanup policy SHOULD prevent `.mh/` from growing indefinitely.

---

# 53. Security Boundary

A child receives equal or narrower capabilities than the parent.

Never broader.

Formally:

```text
child capabilities ⊆ parent capabilities
```

Read child:

```text
strict subset
```

Isolated-write child:

```text
same class of tools
different isolated workspace
```

---

# 54. Context Isolation

The main benefit of delegation is not only concurrency.

It is also:

```text
independent context budget
```

A child can inspect a large subsystem without polluting the parent context.

Only the bounded child result crosses back.

---

# 55. No Child Chain-of-Thought Transfer

No private reasoning trace is transferred from child to parent.

Only:

```text
summary
findings
evidence
workspace delta
```

crosses the boundary.

---

# 56. Implementation Order

### Phase A — delegated task identity

Implement child TaskId/ExecutionId lifecycle using v0.3 identities.

### Phase B — read-only delegation

Start with:

```text
access: read
```

No workspace isolation complexity yet.

### Phase C — parallel read delegation

Add bounded parallel children.

### Phase D — isolated writable workspace

Add Git-backed isolated workspace backend.

### Phase E — structured integration

Implement child delta integration and conflict detection.

### Phase F — delegated evidence

Preserve child evidence provenance.

### Phase G — lifecycle cleanup

Garbage collect isolated workspaces and child artifacts.

---

# 57. Minimal v0.4

If scope must be reduced, the minimum useful v0.4 is:

```text
delegate(read)
parallel read delegates
bounded child context
structured child result
durable provenance
```

Writable delegation can then become v0.4.1.

This is preferable to rushing shared mutable multi-agent execution.

# 59. Explicitly Rejected Design

v0.4 does not become:

```text
AgentManager
├── ResearcherAgent
├── PlannerAgent
├── ReviewerAgent
├── CodingAgent
├── SecurityAgent
└── AgentMessageBus
```

Instead:

```text
Agent
  │
  └── delegate(task, access)
           │
           └── isolated execution
```

The model decides what reasoning task is needed.

The runtime provides execution semantics.

---

# 60. Success Criteria

v0.4 is successful when mh can safely perform:

```text
parent asks two children to independently inspect different parts of a repository
```

without copying their full contexts into the parent.

It can also perform:

```text
child implements a change in isolation
```

without modifying the parent workspace until explicit integration.

And:

```text
parent changed meanwhile
```

is handled as a revision conflict rather than silent corruption.

---

# 61. One-Sentence Definition

> **mh v0.4 adds delegation as a bounded, revision-aware execution primitive with isolated context and optional isolated workspace state.**
