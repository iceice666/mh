# mh v0.5 — Durable Agent Runtime Handoff

Repo: `iceice666/mh`

## Context

`mh` is a Rust coding-agent harness built around Programmatic Tool Calling (PTC) with an embedded MicroQuickJS runtime.

The current architecture already has substantial infrastructure:

* durable append-only session journal
* workspace revision tracking
* checkpoint / restore
* PTC runtime
* bounded tool execution
* result handles for large outputs
* steering / interruption
* evidence tracking
* repeat-action detection
* isolated-write child workspaces
* delegation
* parallel `delegate_batch`
* integration + conflict detection
* context compiler with priority-based budgeting
* session resume

Important existing files:

```text
crates/mh/src/
├── agent.rs
├── checkpoint.rs
├── context.rs
├── delegation.rs
├── identity.rs
├── isolation.rs
├── model.rs
├── ptc/
├── session.rs
├── tools/
└── workspace.rs
```

The purpose of v0.5 is **not** to add more basic coding tools.

The primary objective is to make mh behave like a serious long-running coding agent runtime: a task should be able to survive many context windows, delegate substantial work without blocking the root agent, run long-lived processes, resume after interruption/crash, and preserve goal/task state independently of individual model turns.

Core design principle:

> Tasks are durable. Model calls, context windows, PTC executions, child workers, and subprocesses are disposable execution mechanisms.

---

# v0.5 Goal

After v0.5, this should be a realistic workflow:

```sh
mh run "refactor the storage layer, update all callers, add tests, and verify everything" --detach
```

Later:

```sh
mh tasks
mh attach <task>
```

The root agent may:

1. inspect the repo,
2. create multiple delegated workers,
3. continue working while those workers run,
4. poll or join worker results later,
5. integrate isolated changes,
6. roll over to fresh context windows when necessary,
7. keep long-running builds/dev servers alive,
8. survive process restart,
9. explicitly decide when the overall goal has actually been completed.

The task lifecycle must no longer be equivalent to one `Agent::run_session()` invocation.

---

# Current architectural limitations

## 1. Text output currently completes the task

At the moment, the root agent loop effectively has:

```text
model -> PTC -> model -> PTC -> ... -> text -> complete_task()
```

A plain `ModelOutput::Text` therefore means task completion.

This is too weak for long-running agents because a model may emit a textual progress report even though the actual objective remains incomplete.

v0.5 should separate:

```text
conversation output
```

from:

```text
task completion
```

---

## 2. `max_turns` is a task lifetime limit

Current default root configuration has a finite model-turn limit.

This should become a **context-window / execution-window limit**, not the lifetime of the task.

A long-running task must be able to cross arbitrarily many fresh model contexts.

---

## 3. Compaction infrastructure exists but is incomplete

The session event schema already contains:

```rust
SessionEvent::Compacted {
    task_id,
    summary,
}
```

and the context compiler consumes compacted state as sticky context.

However, there is currently no complete automatic compaction / rollover mechanism.

The current behavior is mostly:

```text
event journal
    ↓
priority context selection
    ↓
older items omitted when the budget is exhausted
```

v0.5 needs:

```text
window N
    ↓
durable semantic checkpoint
    ↓
fresh context
    ↓
window N+1
```

---

## 4. Delegation is synchronous

Current primitives:

```js
delegate(...)
delegate_batch(...)
integrate(...)
```

have good semantics, including isolated-write workspaces and revision tracking.

But `delegate()` blocks until the child finishes, and `delegate_batch()` joins all workers before returning.

This prevents root-agent orchestration of genuinely asynchronous work.

---

## 5. Child executions are not first-class durable sessions

Child agents currently have their own task/execution IDs and workspace state, but their conversational/work-state context is reconstructed per turn from roughly:

* delegated objective
* parent-provided context
* workspace revision
* latest PTC result/error

They do not behave like durable root sessions with their own long-lived journal, compaction, resume, steering, and progress lifecycle.

v0.5 should remove this distinction.

---

## 6. `exec()` only models foreground commands

Current `exec()` waits for the subprocess to terminate.

The default timeout is appropriate for ordinary commands but unsuitable for:

* dev servers
* watchers
* QEMU
* Docker Compose
* long builds
* persistent test runners
* interactive processes

Long-running subprocesses must become durable process resources.

---

# Required v0.5 work

Implement the following five features as the core v0.5 milestone.

---

# 1. Durable Goal State + explicit completion

Introduce an explicit durable representation of the task goal.

A possible shape:

```rust
pub struct GoalState {
    pub objective: String,
    pub status: GoalStatus,

    pub acceptance_criteria: Vec<AcceptanceCriterion>,

    pub completed_work: Vec<WorkItem>,
    pub pending_work: Vec<WorkItem>,
    pub blockers: Vec<Blocker>,

    pub current_revision: RevisionId,
    pub last_verified_revision: Option<RevisionId>,
}
```

Exact types are flexible.

Important invariant:

> `ModelOutput::Text` MUST NOT implicitly complete the task.

Text should be treated as an assistant/progress message.

Introduce an explicit model-visible completion primitive, preferably:

```js
finish({
  summary: "...",
  unresolved: [],
  evidence: [...]
})
```

Possible implementation:

```rust
SessionEvent::FinishProposed { ... }
SessionEvent::TaskCompleted { ... }
```

or equivalent.

`finish()` should validate enough runtime state to prevent obviously invalid completion.

At minimum consider:

* unresolved delegated workers
* failed verification evidence
* workspace revision newer than latest successful verification
* explicitly pending work
* integration conflicts

Do not overbuild a second LLM verifier unless needed.

The key architectural requirement is explicit finish semantics.

---

# 2. Automatic context rollover

Convert the existing context budget system into a multi-window system.

Suggested semantics:

```rust
max_turns_per_window
context_soft_limit
context_hard_limit
```

rather than:

```rust
max_turns == task lifetime
```

When a rollover threshold is reached, produce durable compact state.

Example:

```rust
pub struct ContextCheckpoint {
    pub objective: String,

    pub decisions: Vec<Decision>,
    pub completed: Vec<WorkItem>,
    pub pending: Vec<WorkItem>,
    pub blockers: Vec<Blocker>,

    pub important_findings: Vec<Finding>,
    pub failed_approaches: Vec<Failure>,

    pub changed_paths: Vec<PathBuf>,
    pub verification: Vec<EvidenceRecord>,

    pub active_agents: Vec<AgentSnapshot>,
    pub active_processes: Vec<ProcessSnapshot>,

    pub next_actions: Vec<String>,
}
```

This does not have to be the exact schema.

The important property is that the compacted representation is **semantic task state**, not just a prose summary of the conversation.

Persist it through the existing session event mechanism, extending `Compacted` if necessary.

After rollover, construct a fresh model context containing primarily:

```text
system prompt
goal
current user constraints
semantic task state
workspace state
recent critical events
```

Do not replay the entire old transcript.

A task must be able to survive many rollover cycles.

Also ensure `resume` after process restart produces equivalent usable state.

---

# 3. Async delegated agents

Replace delegation-as-RPC with agent handles.

Keep existing synchronous helpers if useful for compatibility, but add first-class asynchronous primitives.

Suggested PTC API:

```js
var a = agent_spawn({
  task: "inspect the parser architecture",
  access: "read",
  context: {...}
});

var b = agent_spawn({
  task: "implement the storage refactor",
  access: "isolated-write",
  context: {...}
});

var s = agent_poll(a);

agent_send(a, "also inspect parser tests");

var result = agent_join(a);

agent_cancel(b);
```

Potential host-level API:

```rust
AgentId agent_spawn(...)
AgentStatus agent_poll(AgentId)
DelegateResult agent_join(AgentId)
void agent_cancel(AgentId)
void agent_send(AgentId, String)
```

Do not introduce JS promises just for this.

MicroQuickJS can remain synchronous. The Rust scheduler is asynchronous/concurrent underneath.

Required agent states should roughly include:

```text
queued
running
waiting
completed
failed
cancelled
```

Persist enough state to the session journal that task inspection and recovery are possible.

The root agent must be able to perform other model/PTC work while children run.

---

# 4. Make every child a durable Session

Refactor execution so root and child agents use the same underlying agent-session abstraction.

Conceptually:

```rust
pub struct AgentExecution {
    pub id: AgentId,
    pub task_id: TaskId,
    pub parent: Option<AgentId>,
    pub session: Session,
    pub workspace: WorkspaceRef,
    pub access: AgentAccess,
}
```

The exact design is open.

Desired invariant:

> A child is not a special mini-agent implementation. It is a normal agent execution with a parent.

Children should therefore naturally gain:

* event journal
* work state
* multiple model turns
* context compaction
* resume
* progress inspection
* cancellation
* steering/message delivery
* evidence
* checkpoints
* process ownership

Keep delegation depth at 1 for v0.5 unless removing it becomes trivial.

Recursive delegation is NOT a requirement for this milestone.

A robust scheduler-managed one-level worker system is preferable to premature recursive agent trees.

---

# 5. Durable background process handles

Split foreground command execution from long-lived process management.

Keep:

```js
exec(...)
```

for normal commands.

Add something like:

```js
var p = process_spawn({
  command: ["cargo", "watch", "-x", "test"]
});

process_poll(p);
process_tail(p, 100);
process_wait(p);
process_kill(p);
```

Optional later:

```js
process_write(p, "...");
```

and PTY support.

Minimum process state:

```rust
ProcessId
owner_task
owner_agent
argv
cwd
pid
status
started_at
exit_code
stdout handle/log
stderr handle/log
```

Process state should be visible through task inspection.

Consider what process restart can realistically preserve.

It is acceptable for v0.5 to distinguish:

```text
durable metadata
```

from:

```text
OS process survives mh daemon restart
```

If full process reattachment is difficult, persist process metadata and explicitly mark orphaned/dead processes after recovery rather than pretending they survived.

# Runtime architecture

Strongly consider introducing a runtime/service layer rather than putting all orchestration inside `Agent<M>`.

Suggested direction:

```text
CLI
 │
 ▼
Runtime
 ├── TaskManager
 ├── AgentManager
 ├── ProcessManager
 ├── SessionStore
 ├── WorkspaceManager
 └── Model backend
```

Eventually this may become an `mhd` daemon.

For v0.5, a daemon is strongly preferred if it can be implemented without destabilizing the core runtime.

Desired CLI direction:

```sh
mh run "..." --detach

mh tasks

mh inspect <task-id>

mh attach <task-id>

mh steer <task-id> "..."

mh cancel <task-id>
```

Do not spend excessive time polishing TUI/UX before the runtime model works.

---

# Task state machine

Introduce an explicit task lifecycle.

Something approximately like:

```text
queued
running
waiting-agent
waiting-process
waiting-user
blocked
verifying
completed
failed
cancelled
```

Do not infer all task state from whether a model call happens to be active.

Persist state transitions.

---

# Task graph

If time permits after the five core items, introduce persistent work items / dependency tracking.

Prefer a scheduler-managed DAG over recursive delegation.

Possible model-visible API:

```js
task_create(...)
task_depend(...)
task_assign(...)
task_complete(...)
task_list(...)
```

Example:

```text
inspect parser ─────┐
                    ├── implement refactor ── verify
inspect tests ──────┘
```

This is P1 for v0.5, not required before the five core features.

---

# Agent profiles

Also P1.

Extend delegated workers to optionally support profiles:

```js
agent_spawn({
  task: "...",
  profile: "explore",
  access: "read"
});
```

Possible profiles:

```text
explore
implement
review
test
```

Profiles may control:

* model
* system prompt
* tool capabilities
* write permissions
* execution budget

Do not hardcode a large framework yet.

A small declarative mechanism is enough.

---

# Existing architecture to preserve

Do not regress the following existing mh properties:

## PTC-first interface

Provider-facing model API should remain extremely small.

The model currently emits essentially one provider tool:

```text
ptc({ source })
```

Keep this philosophy.

New agent/process/task primitives should be available inside PTC rather than exposed as dozens of provider function schemas.

---

## MicroQuickJS

Do not replace MicroQuickJS merely to obtain async JavaScript.

PTC source may stay synchronous.

Concurrency belongs in the host runtime.

---

## Revision-aware evidence

Existing evidence is tied to workspace revisions.

Preserve this.

Integration should continue invalidating/requiring re-verification where appropriate.

---

## Isolated writes

Writing delegates should continue to work through isolated workspaces rather than multiple agents racing on the same mutable parent tree.

Preserve existing integration conflict behavior.

---

## Bounded execution

Maintain explicit budgets for:

* PTC host calls
* child count
* parallel children
* model turns per context window
* output size
* process resources

Long-running does not mean unbounded resource consumption.

---

# Suggested implementation order

Implement in this order:

## Phase 1 — completion lifecycle

1. Add durable `GoalState`.
2. Make text output non-terminal.
3. Add explicit `finish()`.
4. Update session replay/resume.
5. Add tests proving text output alone cannot complete a task.

## Phase 2 — rollover

1. Add automatic compaction trigger.
2. Generate semantic compact state.
3. Persist it.
4. start a fresh context window.
5. remove task-level turn limit.
6. add tests for >1 context-window task execution.
7. add restart/resume test across a compacted task.

## Phase 3 — worker runtime

1. Introduce `AgentId`.
2. Extract child execution into reusable agent runtime.
3. implement `agent_spawn`.
4. implement `agent_poll`.
5. implement `agent_join`.
6. implement `agent_cancel`.
7. implement parent-to-child messages.
8. persist worker lifecycle events.

## Phase 4 — process runtime

1. Introduce `ProcessId`.
2. implement `process_spawn`.
3. capture stdout/stderr incrementally.
4. implement poll/tail/wait/kill.
5. associate processes with task/agent ownership.
6. handle cleanup and recovery semantics.

## Phase 5 — detached runtime

1. Add runtime manager / daemon boundary.
2. detach task execution from CLI lifetime.
3. add tasks/inspect/attach/steer/cancel commands.
4. test crash/restart behavior.

# Tests required

Do not consider v0.5 complete without integration tests covering long-horizon behavior.

At minimum:

### Explicit finish

Model emits:

```text
"Implemented most of it."
```

Task must remain active.

Only `finish()` completes it.

---

### Context rollover

Use a fake model to force enough turns/context to require at least two rollovers.

Assert:

* same task ID survives
* goal survives
* pending work survives
* workspace state survives
* task can eventually complete

---

### Resume

Interrupt/restart during an active task.

Call `mh resume` or runtime equivalent.

Task continues from persisted semantic state instead of starting over.

---

### Async workers

Root spawns A and B.

Assert:

* A and B overlap in execution
* root can execute another PTC action before joining
* results can be polled independently
* cancellation affects only the selected worker

---

### Durable child context

Force a child to need many turns and at least one context rollover.

Verify an early finding remains represented after rollover.

---

### Isolated integration

Two write agents fork from the same revision.

Verify:

* non-conflicting integration succeeds
* conflicting integration reports conflict
* parent revision tracking remains correct
* verification is marked stale where required

---

### Background process

Spawn a process that lives longer than an ordinary `exec()` timeout.

Assert:

* `process_spawn()` returns quickly
* process remains running
* output can be tailed
* root agent continues work
* process can be killed cleanly

---

### Runtime restart

If daemon support lands:

1. start task
2. create child workers
3. persist state
4. terminate runtime
5. restart runtime

Recovered task must clearly represent:

* task status
* worker states
* workspace revision
* compacted context
* process states/orphans

No silent state loss.

---

# Definition of Done

v0.5 is done when this conceptual execution is real:

```text
durable task
   │
   ├── context window 1
   │      ├── root work
   │      ├── spawn worker A
   │      └── spawn worker B
   │
   ├── rollover
   │
   ├── context window 2
   │      ├── inspect worker A
   │      ├── continue root work
   │      ├── background build
   │      └── integrate worker B
   │
   ├── runtime restart / resume
   │
   ├── context window 3
   │      ├── inspect build
   │      ├── fix failures
   │      └── verify
   │
   └── explicit finish()
```

The user should no longer need to care how many model turns, context windows, child workers, or process executions were required.

From the user's perspective there is only:

```text
task started
task is working
task can be inspected/steered
task finished
```

That is the architectural target for mh v0.5.
