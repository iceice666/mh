# mh v0.3 — Workspace State Runtime Specification

**Status:** Draft / Implementation-ready
**Target:** v0.3
**Previous release:** v0.2
**Primary implementation language:** Rust
**PTC runtime:** MicroQuickJS

---

## 1. Overview

`mh` v0.3 extends the existing PTC workflow runtime with a first-class model of **workspace state**.

v0.2 already provides:

* bounded MicroQuickJS execution;
* host-side parallel `batch()`;
* per-host-call tracing;
* durable session events;
* `WorkState`;
* mutation epochs;
* verification evidence;
* steering;
* stale model-output suppression;
* structured PTC diagnostics;
* symlink-safe filesystem operations.

These are present in the current implementation.

The remaining correctness problem is that `mutation_epoch` is only advanced for successful `write` and `edit` calls, while `exec` may arbitrarily modify the workspace.

For example:

```js
exec({
    command: ["cargo", "fmt"]
});
```

may change source files without incrementing the current mutation epoch.

Similarly, PTC events are currently accumulated during execution and translated into durable session events after the PTC program returns.

Therefore:

```text
filesystem state
```

and:

```text
session state
```

may diverge if the process crashes between a mutation and event persistence.

v0.3 solves this by introducing:

> **WorkspaceRevision as the authoritative identity of workspace state.**

The release thesis is:

> **v0.1 executes programs.
> v0.2 executes workflows.
> v0.3 tracks the state those workflows actually produced.**

---

# 2. Goals

v0.3 MUST provide:

1. first-class workspace revisions;
2. workspace deltas;
3. external mutation detection;
4. process mutation detection;
5. revision-based verification evidence;
6. durable live PTC journaling;
7. crash reconciliation;
8. task episodes;
9. explicit workspace checkpoints;
10. explicit workspace restore;
11. inference supersession;
12. revision-aware context state;
13. provenance IDs suitable for future delegation.

---

# 3. Non-Goals

v0.3 does not include:

* subagents;
* `delegate()`;
* parallel model reasoning;
* agent personas;
* generic plugin APIs;
* distributed execution;
* network tools;
* generic sandbox framework;
* mandatory container execution;
* semantic merge of divergent agent work;
* full Git abstraction;
* automatic commits;
* automatic rollback on every failure.

Subagents are intentionally deferred until workspace state semantics are reliable.

---

# 4. Core Invariants

## 4.1 Workspace state has an identity

At every safe execution boundary, mh MUST be able to answer:

```text
What workspace revision are we currently at?
```

using:

```rust
RevisionId
```

A monotonically increasing integer alone is insufficient.

---

## 4.2 Evidence belongs to a revision

Verification evidence is fresh iff:

```text
evidence.revision == current workspace revision
```

Not:

```text
evidence.mutation_epoch == current mutation epoch
```

---

## 4.3 Processes may mutate the workspace

`exec` MUST NOT be assumed read-only with respect to the workspace.

Current `ProcessPolicy::WorkspaceCwd` explicitly provides cwd/lifetime/output control, not OS-level filesystem isolation.

Therefore every successful process invocation is potentially:

```text
Process + WorkspaceMutation
```

until proven otherwise by revision comparison.

---

## 4.4 Durable history follows successful mutations

After a successful mutation becomes externally visible, mh MUST persist sufficient revision information before proceeding past the next durability boundary.

The following must not be possible:

```text
filesystem mutated
↓
agent continues
↓
crash
↓
resume believes old workspace revision is current
```

---

## 4.5 External writers are legitimate

mh is not assumed to be the sole workspace writer.

Users may modify files using:

* an editor;
* formatter;
* Git;
* IDE;
* build scripts;
* another terminal.

Such changes MUST be detected and represented as workspace drift rather than ignored.

---

# 5. Identity Types

v0.3 introduces explicit identities.

Recommended definitions:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct TaskId(pub u64);

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct ExecutionId(pub u64);

#[derive(Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct RevisionId(pub String);

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct CheckpointId(pub u64);
```

`TaskId` and `ExecutionId` are introduced now even though v0.3 remains single-agent.

This avoids adding provenance retroactively when delegation is implemented.

---

# 6. Task Identity

A **Task** represents one user-level objective.

Example:

```text
Task 14:
"fix the parser tests"
```

It is not identical to the workspace session.

A workspace session may contain many tasks.

---

# 7. Execution Identity

An **Execution** represents one model-driven operational unit.

Initially:

```text
one PTC execution = one ExecutionId
```

Future delegation may create additional execution types.

Every durable host-call event SHOULD include:

```text
task_id
execution_id
```

---

# 8. WorkspaceRevision

Recommended representation:

```rust
pub struct WorkspaceRevision {
    pub id: RevisionId,

    pub sequence: u64,

    pub parent: Option<RevisionId>,

    pub changed_paths: Vec<PathBuf>,

    pub detected_at_ms: u64,
}
```

`sequence` is human-friendly ordering.

`id` is authoritative identity.

---

# 9. RevisionId Semantics

A `RevisionId` MUST identify relevant workspace filesystem state.

The exact backend may differ.

Preferred priority:

```text
Git workspace
    ↓
Git-aware revision backend

non-Git workspace
    ↓
filesystem fingerprint backend
```

---

# 10. Git-Aware Revision Backend

For Git repositories, revision identity SHOULD represent:

```text
HEAD
+
tracked working tree state
+
relevant untracked files
```

It MUST NOT depend on the user's staging area alone.

The implementation MUST NOT modify the user's real Git index merely to compute identity.

A valid backend may use:

* temporary index;
* Git tree hashing;
* file metadata plus content hashes;
* another deterministic Git-aware mechanism.

Exact implementation is not part of the stable public ABI.

---

# 11. Filesystem Revision Backend

For non-Git workspaces, mh SHOULD compute a deterministic fingerprint of relevant files.

Conceptually:

```text
sorted path
+
file type
+
content hash
```

Directories such as:

```text
.mh/
.git/
target/
node_modules/
```

MAY be excluded by policy.

The exclusion policy MUST be deterministic.

---

# 12. WorkspaceTracker

Introduce:

```rust
pub trait WorkspaceTracker {
    fn current_revision(&self) -> Result<WorkspaceRevision, WorkspaceError>;

    fn delta(
        &self,
        from: &RevisionId,
        to: &RevisionId,
    ) -> Result<WorkspaceDelta, WorkspaceError>;
}
```

Recommended delta:

```rust
pub struct WorkspaceDelta {
    pub from: RevisionId,
    pub to: RevisionId,

    pub added: Vec<PathBuf>,
    pub modified: Vec<PathBuf>,
    pub deleted: Vec<PathBuf>,
}
```

---

# 13. Revision Boundaries

Workspace revision checks SHOULD occur:

```text
before PTC
after successful write/edit
after exec
after PTC
before model inference
on resume
after steering if external edits may have occurred
```

The runtime MAY coalesce redundant checks when correctness is preserved.

---

# 14. Tool Effects v2

The current single-valued effect enum is insufficient because a process may also mutate the workspace.

Replace or evolve:

```rust
pub enum ToolEffect {
    ReadOnly,
    WorkspaceMutation,
    Process,
    Meta,
}
```

into a composable structure:

```rust
#[derive(Debug, Clone, Copy, Default, Serialize, Deserialize)]
pub struct ToolEffects {
    pub reads_workspace: bool,
    pub mutates_workspace: bool,
    pub process: bool,
    pub meta: bool,
}
```

Examples:

```text
read
→ reads_workspace

edit
→ reads_workspace + mutates_workspace

exec cargo test
→ process

exec cargo fmt
→ process + mutates_workspace
```

The last classification is determined from revision comparison, not command-name heuristics.

---

# 15. Process Mutation Detection

Before `exec`:

```text
R_before
```

After `exec`:

```text
R_after
```

If:

```text
R_before != R_after
```

the host event MUST record:

```text
workspace mutation occurred
```

and SHOULD include:

```text
changed paths
```

from the tracker.

This works for arbitrary model-generated commands.

---

# 16. Revision Transition Event

Add a durable event:

```rust
SessionEvent::WorkspaceRevisionChanged {
    task_id: TaskId,
    execution_id: Option<ExecutionId>,

    from: RevisionId,
    to: RevisionId,

    added: Vec<String>,
    modified: Vec<String>,
    deleted: Vec<String>,

    source: RevisionSource,
}
```

Recommended source:

```rust
pub enum RevisionSource {
    Tool,
    Process,
    External,
    Restore,
}
```

---

# 17. Durable PTC Event Sink

Current v0.2 PTC events are accumulated in-memory inside `PtcResult` and translated into session events afterward.

v0.3 introduces:

```rust
pub trait PtcEventSink {
    fn emit(&mut self, event: PtcEvent) -> Result<(), PtcEventSinkError>;
}
```

`PtcRuntime` MUST emit relevant events during execution rather than only returning them afterward.

---

# 18. Event Sink Composition

The runtime MAY support multiple sinks:

```text
PtcRuntime
   │
   ├── durable session sink
   ├── live AgentEvent sink
   └── optional in-memory collector
```

Recommended:

```rust
pub struct CompositePtcEventSink<...> {
    ...
}
```

No generic plugin system is implied.

---

# 19. Durability Policy

Not every trace event requires `fsync`.

Recommended policy:

```text
HostCallStarted
→ best effort

read-only HostCallCompleted
→ append, batching allowed

workspace revision transition
→ durable boundary

checkpoint creation
→ durable boundary

restore completion
→ durable boundary
```

Exact fsync strategy MAY be tuned later.

Correctness requirement:

> A durable revision transition must never describe filesystem state that had not already become visible.

---

# 20. Crash Reconciliation

On:

```bash
mh resume
```

mh MUST compare:

```text
last persisted workspace revision
```

with:

```text
actual current workspace revision
```

If equal:

```text
normal resume
```

If different:

```rust
SessionEvent::WorkspaceDriftDetected {
    expected: RevisionId,
    actual: RevisionId,
    delta: WorkspaceDelta,
}
```

is appended.

---

# 21. Workspace Drift

Workspace drift covers:

```text
mh crashed after mutation
external editor changed files
git checkout happened
formatter ran outside mh
another process changed workspace
```

It is not treated as corruption.

Instead:

```text
new workspace revision becomes authoritative
```

and old evidence becomes stale.

---

# 22. Evidence v2

Current evidence records contain:

```rust
mutation_epoch: u64
```

v0.3 changes them to:

```rust
pub struct EvidenceRecord {
    pub kind: String,
    pub ok: bool,

    pub revision: RevisionId,

    pub result_ids: Vec<ResultId>,
    pub note: Option<String>,

    pub timestamp_ms: u64,

    pub task_id: TaskId,
    pub execution_id: ExecutionId,
}
```

---

# 23. Evidence Freshness

Freshness is derived:

```rust
pub enum EvidenceFreshness {
    Fresh,
    Stale,
}
```

Rule:

```text
record.revision == current_revision.id
```

No separate persisted freshness flag is necessary.

---

# 24. PTC `evidence()`

The PTC API remains:

```js
evidence(kind, ok, metadata)
```

Example:

```js
var r = exec({
    command: ["cargo", "test"]
});

evidence("tests", r.exitCode === 0, {
    stdout: r.stdout.id,
    stderr: r.stderr.id
});
```

The host automatically attaches:

```text
task_id
execution_id
current RevisionId
```

The model does not provide these.

---

# 25. Task Episodes

Current session state keeps one original `task` across the workspace session.

v0.3 introduces multiple task episodes.

Events:

```rust
SessionEvent::TaskStarted {
    task_id: TaskId,
    objective: String,
    base_revision: RevisionId,
}

SessionEvent::TaskCompleted {
    task_id: TaskId,
    final_revision: RevisionId,
    answer: Option<String>,
}

SessionEvent::TaskInterrupted {
    task_id: TaskId,
}
```

---

# 26. SessionState v3

Recommended:

```rust
pub struct SessionState {
    pub id: String,
    pub workspace: PathBuf,

    pub active_task: Option<TaskId>,

    pub current_revision: RevisionId,

    pub last_event_seq: u64,

    pub created_at_ms: u64,
    pub updated_at_ms: u64,

```

The original:

```rust
task: Option<String>
```

should be migrated into Task events.

# 27. WorkState v3

Recommended:

```rust
pub struct WorkState {
    pub task_id: Option<TaskId>,
    pub objective: Option<String>,

    pub base_revision: Option<RevisionId>,
    pub current_revision: RevisionId,

    pub latest_user_message: Option<String>,

    pub changed_paths: Vec<PathBuf>,

    pub latest_ptc: Option<PtcSummary>,
    pub latest_failure: Option<PtcSummary>,

```

`touched_files` MAY remain as derived historical metadata, but correctness-sensitive logic SHOULD use revision delta.

# 28. Context Compiler v3

The working-state section SHOULD become:

```text
[working state]
task: 17
base revision: 8892a1
current revision: c23ef0

workspace changes:
- modified src/parser.rs
- added tests/parser.rs

verification:
- cargo test: PASS @ c23ef0 — fresh
- cargo clippy: PASS @ 8892a1 — stale
```

The model should not need to infer workspace freshness from chronological dialogue.

# 29. Checkpoints

v0.3 introduces explicit workspace checkpoints.

Canonical PTC API:

```js
var cp = checkpoint();
```

It returns:

```js
{
    id: 42,
    revision: "c23ef0"
}
```

---

# 30. Checkpoint Semantics

A checkpoint captures sufficient information to restore the workspace to the recorded revision.

Checkpoint creation MUST NOT:

* create a user-visible Git commit;
* modify the user's staging area;
* modify branch refs.

---

# 31. Git Checkpoints

For Git workspaces, the preferred implementation is a hidden Git object or temporary-index snapshot.

Possible approach:

```text
temporary index
    ↓
git add -A
    ↓
git write-tree
    ↓
TreeId
```

Stored metadata:

```rust
pub struct Checkpoint {
    pub id: CheckpointId,
    pub revision: RevisionId,
    pub backend: CheckpointBackend,
}
```

---

# 32. Filesystem Checkpoints

Non-Git workspaces MAY initially use:

```text
copy-on-write backup
```

or:

```text
snapshot directory under .mh/
```

A size limit SHOULD exist.

If reliable checkpointing is unavailable:

```js
checkpoint()
```

returns a structured error rather than pretending to succeed.

---

# 33. Restore

Canonical API:

```js
restore(cp);
```

After successful restore:

```text
current workspace revision = checkpoint revision
```

A durable:

```rust
WorkspaceRevisionChanged {
    source: Restore,
    ...
}
```

event MUST be emitted.

---

# 34. Explicit Restore Only

mh MUST NOT automatically restore a checkpoint merely because:

* a PTC program threw;
* tests failed;
* the model changed its mind.

Example:

```js
var cp = checkpoint();

edit(...);

var r = exec(...);

if (r.exitCode !== 0) {
    restore(cp);
}
```

The model chooses transaction semantics explicitly.

---

# 35. No Nested Transaction Model

v0.3 does not introduce:

```text
begin_transaction
commit_transaction
nested savepoint
```

`checkpoint()` is a snapshot primitive.

`restore()` restores workspace state.

That is sufficient.

---

# 36. Checkpoint Lifetime

Checkpoints SHOULD be task-scoped by default.

They MAY remain persisted for crash recovery during the active task.

Old checkpoints MAY be garbage collected after task completion.

---

# 37. Superseded Inference

v0.2 correctly suppresses stale model output after steering, but waits for the current model request to finish first.

v0.3 introduces distinct cancellation reasons.

Recommended:

```rust
pub enum GenerationStop {
    UserInterrupt,
    Superseded,
}
```

---

# 38. Steering During Inference

When steering arrives:

```text
model generating
↓
user steering arrives
```

mh SHOULD terminate the active generation request as:

```text
Superseded
```

then:

```text
append steering
recompile context
start replacement generation
```

---

# 39. Superseded Is Not Interrupted

A superseded request MUST NOT mark the task as:

```text
Interrupted
```

It is normal control flow.

Possible event:

```rust
SessionEvent::ModelSuperseded {
    task_id: TaskId,
}
```

---

# 40. Workspace Reconciliation Before Inference

Immediately before each model inference, mh SHOULD ensure:

```text
session current_revision == actual workspace revision
```

If not, reconcile first.

This ensures external edits become visible before reasoning continues.

---

# 41. PTCResult v3

`PtcResult` SHOULD include:

```rust
pub struct PtcResult {
    pub value: Value,
    pub outcome: PtcOutcome,

    pub task_id: TaskId,
    pub execution_id: ExecutionId,

    pub start_revision: RevisionId,
    pub end_revision: RevisionId,

    pub tool_calls: usize,
    pub duration_ms: u64,

    pub diagnostic: Option<PtcDiagnostic>,
}
```

Its event list MAY become optional because live sinks become authoritative.

# 42. Process Capability

v0.3 retains:

```text
WorkspaceCwd
```

semantics.

It still does not mean sandboxed.

Current implementation scrubs provider credentials from child processes, including `MH_API_KEY` and `OPENAI_API_KEY`.

That behavior MUST remain.

---

# 43. Experimental Process Sandbox Boundary

The capability type MAY evolve to:

```rust
pub enum ProcessPolicy {
    Disabled,
    HostWorkspace,
    SandboxedWorkspace,
}
```

Only:

```text
Disabled
HostWorkspace
```

must be implemented in v0.3.

`SandboxedWorkspace` may return:

```text
unsupported
```

until a backend exists.

---

# 44. Session Migration

Opening a v0.2 session MUST either:

1. migrate it safely; or
2. reject it with an explicit version error.

Preferred migration:

```text
derive initial TaskStarted from old state.task
compute actual workspace RevisionId
mark old evidence as legacy/stale unless mapped safely
append SessionMigrated event
```

Old mutation epochs MUST NOT be interpreted as revision identity.

# 47. Example Workflow

```js
var cp = checkpoint();

edit({
    path: "src/parser.rs",
    old: "old implementation",
    new: "new implementation"
});

var fmt = exec({
    command: ["cargo", "fmt"]
});

var tests = exec({
    command: ["cargo", "test"]
});

if (tests.exitCode !== 0) {
    restore(cp);

    return {
        fixed: false,
        errors: tests.stderr.tail(80)
    };
}

evidence("tests", true, {
    stdout: tests.stdout.id
});

return {
    fixed: true
};
```

Host state might become:

```text
checkpoint: R10

edit:
R10 → R11

cargo fmt:
R11 → R12

cargo test:
R12 → R12

evidence:
PASS @ R12
```

# 48. External Edit Example

During model inference:

```text
current revision: R20
```

User edits:

```text
src/foo.rs
```

outside mh.

Before the next inference:

```text
tracker sees R21
```

mh emits:

```text
WorkspaceDriftDetected
R20 → R21
```

Existing evidence at R20 becomes stale.

No special user command is required.

---

# 49. Crash Example

```text
PTC begins @ R30
edit foo.rs
workspace becomes R31
revision event persisted
process crashes
```

On resume:

```text
actual = R31
persisted = R31
```

normal recovery.

If crash occurs before revision event durability:

```text
actual = R31
persisted = R30
```

resume reconciles:

```text
WorkspaceDriftDetected
R30 → R31
```

The state repairs itself.

# 50. Implementation Order

### Phase A — identity

Implement:

```text
TaskId
ExecutionId
RevisionId
WorkspaceRevision
WorkspaceDelta
WorkspaceTracker
```

### Phase B — process/revision tracking

Wrap mutations and `exec` with before/after revision comparison.

### Phase C — live event sink

Move PTC host-call persistence from post-execution translation to live journaling.

### Phase D — evidence migration

Replace mutation-epoch freshness with revision freshness.

### Phase E — task episodes

Migrate session root-task semantics into explicit task events.

### Phase F — crash reconciliation

Compare persisted and actual revision on open/resume.

### Phase G — checkpoint/restore

Implement Git backend first.

### Phase H — inference supersession

Differentiate user interrupt from steering replacement.
